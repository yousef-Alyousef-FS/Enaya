Enaya — Push Notifications Implementation Guide (Flutter)

This document explains everything needed to add Firebase Cloud Messaging (FCM) push notifications to the Flutter app (shared codebase, 3 roles: Doctor, Receptionist, Patient).

The backend is already fully built and working. This guide covers only the Flutter side.

Step 1

What we're building — the big picture

Our Laravel backend can already send push notifications for events like:

  • New appointment created (notifies the doctor)
  • Appointment cancelled / rescheduled
  • New prescription issued
  • Session started / completed

For any of this to reach a phone, the backend needs to know which device belongs to which logged-in user. That's the only job of the Flutter side: get the phone's unique FCM token, tell the backend about it at the right moments, and handle displaying notifications when they arrive.

Think of the FCM token as a "mailbox address" for that specific phone install. Firebase handles actually delivering messages to phones — our backend just tells Firebase "deliver to mailbox X," Firebase does the rest, even if the app is closed.

ℹ️Nothing here needs Supabase. Supabase is only used for our database/backend deployment — it has no role in push notifications. Only Firebase (FCM) delivers pushes.
Step 2

Firebase project setup (one-time, do this first)

Go to console.firebase.google.com and create a new Firebase project (or ask whoever set up the backend — they may have already created one for the Laravel side; if so, reuse that same project instead of creating a second one).

Install the FlutterFire CLI if not already installed:

bash
dart pub global activate flutterfire_cli

From the root of the Flutter project, run:

bash
flutterfire configure

This walks you through selecting your Firebase project and generates a firebase_options.dart file, plus registers the app with Firebase for each platform (Android/iOS) you select. Since it's one shared codebase for all 3 roles, you only need to run this once — it's one Flutter app registered with Firebase, not three.

Step 3

Add the required packages

In pubspec.yaml:

yaml
dependencies:
  firebase_core: ^latest
  firebase_messaging: ^latest

Run flutter pub get after adding them. (Check current stable versions on pub.dev at the time you do this — don't hardcode a version here since it'll go stale.)

Step 4

Initialize Firebase on app startup

In main.dart:

dart
import 'package:firebase_core/firebase_core.dart';
import 'firebase_options.dart';

Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await Firebase.initializeApp(
    options: DefaultFirebaseOptions.currentPlatform,
  );
  runApp(const MyApp());
}
Step 5

Request notification permission

Required on iOS, and on Android 13+. Call this once, early in the app lifecycle (e.g. right after Firebase initializes, or right before you register a token):

dart
FirebaseMessaging messaging = FirebaseMessaging.instance;

NotificationSettings settings = await messaging.requestPermission(
  alert: true,
  badge: true,
  sound: true,
);
⚠️If the user denies permission, getToken() will still technically work on some platforms but the phone won't display the notification — no special handling needed beyond this, just be aware denial is possible.
Step 6

Backend endpoint you'll be calling

POST /api/device-token

Auth: requires the Sanctum bearer token (same as any other authenticated request)

Body:

json
{
    "fcm_token": "the long token string from Firebase",
    "device_type": "android"
}

device_type is optional ("android" or "ios").

Response: standard envelope, { success, data, error, errorCode }

✅Calling this endpoint repeatedly with the same token is completely safe — the backend uses updateOrCreate, so there's no risk of duplicate rows from calling it more than once.

Base URL: use the production Vercel URL for the API — get the current URL from whoever manages the deployment, since it may differ between environments. Store it in whatever config/env setup the app already uses for its API base URL (don't hardcode it separately just for this feature).

Step 7

When to register the token — the 3 required moments

A. Right after successful login

The moment /login returns a Sanctum token, immediately:

dart
Future<void> registerDeviceToken(String sanctumToken) async {
  final fcmToken = await FirebaseMessaging.instance.getToken();
  if (fcmToken == null) return;

  await dio.post(
    '/device-token',
    data: {
      'fcm_token': fcmToken,
      'device_type': Platform.isAndroid ? 'android' : 'ios',
    },
    options: Options(headers: {'Authorization': 'Bearer $sanctumToken'}),
  );
}

Call this right after storing the Sanctum token from the login response.

B. Right after successful signup

Exact same call, right after /register succeeds and you have a Sanctum token — whichever role is signing up (if patients self-register; doctors/receptionists are likely created by an admin instead, so this may only apply to the Patient role — confirm with the team which roles actually have a signup flow in the app).

C. Whenever the token refreshes

FCM tokens can rotate (reinstall, OS-level refresh, etc). Set up a listener once, anywhere central (e.g. in main.dart or an app-wide service):

dart
FirebaseMessaging.instance.onTokenRefresh.listen((newToken) {
  // only call this if the user is currently logged in —
  // check your auth state before sending
  registerDeviceToken(currentSanctumToken);
});
Step 8

Logout — send the token so the backend can remove it

POST /logout

Now optionally accepts an fcm_token field. Before logging out, include the current token:

dart
Future<void> logout(String sanctumToken) async {
  final fcmToken = await FirebaseMessaging.instance.getToken();

  await dio.post(
    '/logout',
    data: {'fcm_token': fcmToken},
    options: Options(headers: {'Authorization': 'Bearer $sanctumToken'}),
  );
}

This removes just this device's registration — important because a user might be logged in on multiple devices at once, and logging out on one shouldn't kill push for the others.

Step 9

Receiving and displaying notifications — the 3 app states

A push can arrive while the app is in any of these states, and each needs different handling.

State 1 — App open (foreground)

Foreground messages do not auto-display as a system notification — you must show something yourself (snackbar, in-app banner, dialog, etc.):

dart
FirebaseMessaging.onMessage.listen((RemoteMessage message) {
  final title = message.notification?.title ?? '';
  final body = message.notification?.body ?? '';
  // show your own UI here, e.g. a SnackBar or in-app banner
  showInAppNotification(title, body);
});

State 2 — App in background (minimized, not closed)

The system shows the notification automatically. You only need a top-level function (outside any class) registered as the background handler, so Flutter can call it even when the app isn't actively running in the foreground:

dart
@pragma('vm:entry-point')
Future<void> firebaseMessagingBackgroundHandler(RemoteMessage message) async {
  await Firebase.initializeApp(options: DefaultFirebaseOptions.currentPlatform);
  // any background processing needed can go here — usually nothing extra required,
  // the system displays the notification on its own
}

Register it in main(), before runApp():

dart
FirebaseMessaging.onBackgroundMessage(firebaseMessagingBackgroundHandler);

State 3 — App fully closed (terminated)

Same background handler above covers delivery. Additionally, check on startup whether the app was launched by tapping a notification:

dart
Future<void> checkInitialMessage() async {
  RemoteMessage? initialMessage =
      await FirebaseMessaging.instance.getInitialMessage();
  if (initialMessage != null) {
    handleNotificationTap(initialMessage);
  }
}

Call this once during app startup (e.g. in your splash/init screen).

Step 10

Tap-to-navigate using the data payload

Every notification the backend sends includes a data payload alongside the visible title/body, shaped like:

json
{ "type": "appointment", "id": "42" }

(the exact type value varies — e.g. appointment_cancelled, appointment_rescheduled, prescription, session_in_progress, session_completed, session_cancelled)

Use this to route the user to the right screen when they tap a notification:

dart
void handleNotificationTap(RemoteMessage message) {
  final type = message.data['type'];
  final id = message.data['id'];

  switch (type) {
    case 'appointment':
    case 'appointment_cancelled':
    case 'appointment_rescheduled':
      navigatorKey.currentState?.pushNamed('/appointment-details', arguments: id);
      break;
    case 'prescription':
      navigatorKey.currentState?.pushNamed('/prescription-details', arguments: id);
      break;
    case 'session_in_progress':
    case 'session_completed':
    case 'session_cancelled':
      navigatorKey.currentState?.pushNamed('/session-details', arguments: id);
      break;
  }
}

Wire this into both the foreground tap handler and the getInitialMessage() check from Section 9.

Also listen for taps while the app is in the background (not terminated):

dart
FirebaseMessaging.onMessageOpenedApp.listen((RemoteMessage message) {
  handleNotificationTap(message);
});
Step 11

Suggested build order

  1. Run flutterfire configure, add packages, initialize Firebase in main.dart
  2. Request permission, confirm you can print a real token to console
  3. Wire up token registration after login (Section 7A)
  4. Manually confirm the token lands in the backend's device_tokens table
  5. Trigger a real event from the backend (e.g. create an appointment for that logged-in doctor) and confirm a push actually arrives on the physical device/emulator
  6. Add foreground handling (Section 9, State 1) so open-app notifications show something
  7. Add background handler + getInitialMessage() (Section 9, States 2 & 3)
  8. Add tap-to-navigate (Section 10)
  9. Add signup registration (Section 7B) and logout token removal (Section 8)
  10. Repeat testing for the other 2 roles, since it's one shared codebase — confirm role-based navigation targets in Section 10 make sense per role
Step 12

Common gotchas

  • iOS push testing requires a real device — the iOS simulator cannot receive real push notifications. Android emulators generally can, as long as they have Google Play services.
  • Foreground messages showing nothing is expected, not a bug — you must build the in-app display yourself (Section 9, State 1).
  • getToken() returning null usually means permission wasn't granted yet, or Firebase hasn't finished initializing — make sure requestPermission() and Firebase.initializeApp() both complete before calling it.
  • Background handler not firing — it must be a top-level function (not inside a class/widget) and annotated with @pragma('vm:entry-point'), or Android can strip it during release builds.
